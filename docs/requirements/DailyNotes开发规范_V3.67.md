## 0. 核心数据架构硬约束（每次接手必须先读）

> **手机唯一权威存储；PC 远程编辑；WebDAV 完全手动。**

1. Android 手机是 DailyNotes 唯一正式数据中心。所有正式日记、笔记、长期记录、修订、删除状态、附件及业务历史均以手机权威数据库为准。
2. PC 是局域网富文本编辑终端。PC 的正式编辑必须传回手机，经手机校验并成功落盘后，才能显示「已保存到手机」；PC 浏览器草稿不是第二套正式数据库。
3. 手机与 PC 在线时自动低延迟双向更新，双端均可发起编辑；但正式持久化权威始终只有手机。手机不可达时，PC 只能保留明确标记的未提交草稿。
4. 坚果云 WebDAV 只在用户主动手动点击同步后运行。任何 LAN 自动同步、保存、WebSocket 事件、应用启动或后台任务都不得自动触发 WebDAV。
5. 未来开发者/AI 接手时，必须先阅读本节、DN-187 与 `docs/research/DailyNotes_Phone_Authoritative_PC_Remote_Editor_Architecture_R009.md`；不得重新提出手机/PC 双权威数据库作为默认架构。

## 0.1 手机局域网 PC 编辑服务运行约束（DN-188）

- 用户选择 A：在手机前台手动开启「PC 编辑模式」，PC 配对连接后维持会话；息屏后允许继续服务，必要时配置后台运行权限。
- 手机托管网页、HTTP API、WebSocket，并继续作为唯一权威数据存储；PC 是浏览器编辑端。
- 优先研究 Android connectedDevice 前台服务类型；不以 dataSync 维持长连接。启动必须由用户可见的手机操作触发，并显示持续状态通知和停止入口。
- 息屏在线是目标，不是 Android/HyperOS 保证。必须处理 Doze/Low Power Standby、HyperOS 后台网络限制、Wi-Fi/IP 变化、服务进程终止和用户停止。
- 默认不持有整个会话的永久 WakeLock；只有实测证明必要时才引入受控短时锁。可按需配置 HyperOS「无限制」，但不得声称它能绕过系统级省电限制。
- Android 17 target SDK 37+ 局域网权限、Android 13+ 通知权限、浏览器 HTTPS/WSS 证书信任与安全配对均为实现前置研究项。
- 完整技术风险、流程与真机验收矩阵见 docs/research/DailyNotes_Phone_LAN_Foreground_Service_Risk_Research_R010.md。本条不代表服务已实现或已通过息屏实测。

## 0.2 PC 手动 IP 连接与信任边界（DN-189）

- 用户选择方案 B：手机显示当前 Wi-Fi IPv4 与候选固定端口，PC 手动输入 HTTPS 地址；首期不使用二维码、mDNS/SSDP 自动发现或全网扫描。
- 手机同源托管 HTTPS 页面、REST API、WSS；IP 只负责定位，TLS 证书验证服务器身份，配对码授予 PC 访问权限。
- TLS 证书使用 SAN 的 iPAddress 精确匹配当前 IP；禁止忽略浏览器证书警告。
- 长期候选：Android Keystore 私有 CA + 当前 IP 动态叶证书；简单 PoC 备选：DHCP 地址保留 + 固定 IP 自签名证书。最终路线须经 AndroidKeyStore、Windows 当前用户信任库和 Chrome 157 实测。
- 首次配对使用手机生成的一次性配对码，首次由手机批准；PC 使用可撤销设备凭证复用授权。具体码长/时效/PC 数量仍待讨论。
- 只绑定手机当前 Wi-Fi 接口；不监听蜂窝/所有接口，不开放公网或端口转发。IP 变化后手机更新地址，PC 手动输入新地址。
- Chrome 同源 local→local 与 Android 17 target SDK 37+ 的 ACCESS_LOCAL_NETWORK 是不同权限问题；手动输入 IP 不豁免 Android 入站 TCP 权限。
- PC 写入以 operationId/baseRevision 幂等提交；手机事务落盘后 ACK；WSS 通知丢失时按 eventSequence 补齐。完整协议、证书、配对及异常恢复研究见 `docs/research/DailyNotes_Manual_IP_Connection_Pairing_TLS_Recovery_Research_R011.md`。本条只确认方向，不代表已实现或已验收。

## 0.3 Windows TLS 证书策略仍待决（DN-190）

- 用户明确选择 C：暂不决定 A/B，继续比较；不授权安装证书、编码或最终选型。
- 路线 A 细化为 CA:FALSE 的自签名服务器终端证书（serverAuth + 当前 IP 的 iPAddress SAN），研究导入 Windows 当前用户 Root store 作为 Chrome trusted leaf；仍需一次信任安装，IP 变化需重新导入。
- 路线 B 为 Android Keystore 私有 CA + 动态叶证书；研究将 CA NameConstraints 收窄到当前 LAN CIDR，避免默认信任全部 RFC1918；同一允许子网内 IP 变化可自动换叶证书。
- Chromium Windows 源码支持 Root store 自签名 trusted leaf，并对平台 trust anchor constraints 执行约束；Current User Root 与 Local Machine / Trusted People 不可混淆。
- 两条路线都要在 Windows 10 + Chrome 157、目标 Android 设备验证；Keystore 非导出不等于硬件保护，需实测 securityLevel。
- 完整比较见 `docs/research/DailyNotes_Certificate_Architecture_Comparison_R012.md`。当前无最终选型，无代码和实机验收。

## 0.4 家庭局域网简化安全架构与逐次手机审批（DN-191）

- 用户明确选择 B：PC 每次新建连接或断线后重新连接，都必须由手机再次人工确认。
- 首期安全模型仅保留三层：当前家庭 Wi-Fi 网络边界、HTTPS/WSS 服务器身份与加密、每次连接的手机人工审批。
- 首期 TLS 目标采用单张 CA:FALSE 自签名服务器终端证书（serverAuth + 当前 Wi-Fi IP 的 iPAddress SAN）；Android Keystore 保存私钥；Windows Current User Root 信任安装须核对 SHA-256 指纹。**不建设私有 CA、不做动态证书签发**；Chrome/Windows 仍须 PoC。建议 DHCP reservation 减少 IP 变化，不强制。
- 取消首期配对码、长期 PC 设备凭证、可信设备列表、记住 PC 和自动授权。
- 每次新建/重建逻辑编辑/WSS 会话都由手机确认；未批准不得读取任何个人数据。手机批准后仅发放当前会话临时 token，断线/超时/服务停止即撤销。
- 同一有效会话中的普通 API 请求和底层 HTTP 连接池重建不反复确认；WSS 断开或心跳超时后恢复连接必须再次确认。
- 手机息屏时通过通知引导用户手动确认，不自动批准。PC 草稿保留，手机仍是唯一权威数据中心，WebDAV 仍只手动触发。
- 详细状态机、风险与验收见 `docs/research/DailyNotes_Simplified_PerConnection_Approval_Security_Research_R013.md`。本条取代 DN-189/DN-190 的首期配对/证书复杂化方案；所有实现和兼容性仍待 PoC/实机验收。

## 0.5 开发投入优先级：优先功能与体验（DN-192）

用户明确要求：**把更多开发时间投入 DailyNotes 的功能完整度与实际使用体验，不要把过多时间耗费在非必要的局域网安全细节讨论上。**

- 保持 DN-191 的最低必要安全边界，不降低手机唯一权威数据、可靠持久化和 HTTPS/WSS 等必要保护。
- 不再单独反复打磨连接请求卡片、通知视觉、企业级证书管理、设备管理或非阻断的安全边界细节；只有当问题实际阻塞功能、数据可靠性或验收时，才开展定向研究与最小验证。
- 后续开发投入优先顺序：
  1. 手机端核心记录与快速编辑体验：日记、笔记、长期记录、待办、AppFlowy 风格富文本。
  2. 手机本机数据可靠性：保存事务、自动保存、崩溃恢复、附件完整性。
  3. PC 局域网富文本编辑，以及 PC 与手机唯一权威存储之间的低延迟更新、可靠提交和冲突保护。
  4. 用户主动手动触发的坚果云 WebDAV 备份与恢复。
  5. 搜索、日历、归档、统计、数据健康等辅助功能。
- 每阶段优先交付可运行、可验证、对日常使用有直接价值的功能；不要为非阻断细节无限扩展设计。
- 本优先级不表示功能已实现，也不允许跳过必要的数据可靠性与安全验收。

## 0.6 手机端统一 AppFlowy 风格编辑器（DN-193）

- 用户明确确认：手机端编辑器直接采用 AppFlowy 风格即可，不再为「快速记录」额外设计一套功能受限的简化编辑器。
- 普通日记、普通笔记、长期记录追加共用同一套移动端文档编辑体验；页面快捷入口/底部上下文加号只负责快速进入同一编辑器，打开后直达正文。入口路径可以轻量，编辑器本身不缩水。
- 交互基线沿用 DN-180 动态工具栏、DN-181 AppFlowy 完整应用移动工具栏源码基线，以及 DN-182 对 + 区块插入、Aa 排版、媒体/附件、文字选区菜单的研究路径。R001～R005 为已有源码研究依据。
- 「像 AppFlowy」指移动端编辑体验和交互参照，不代表已批准所有上游区块/高级功能，不代表直接采用 `appflowy_editor` 依赖、复制全部上游代码或改变 DailyNotes 数据架构；具体功能范围、依赖与许可仍按既有待讨论项处理。
- **业务保存语义绝不因编辑器统一而合并：** 日记按 DN-020/021 自动正式保存；普通笔记按 DN-045/047 自动本机保存并保护失败内容；长期记录追加按 DN-009/010 保留草稿与明确提交边界。编辑器统一，业务生命周期独立。
- 本条细化 DN-009、DN-018、DN-044、DN-178～DN-182；不改变 DN-155 的全局上下文加号行为，不授权编码。

## 0.7 AppFlowy 对标与分阶段功能完整性原则（DN-194）

用户明确确认：**DailyNotes 手机编辑器的外观、交互和功能能力都以 AppFlowy 为参照，分阶段实现，但不随意砍掉功能。**

- 对标对象是 AppFlowy 官方完整应用的真实移动端编辑体验，而非只模仿截图或只使用独立 `appflowy_editor` 示例。范围涵盖文档排版、工具栏、区块结构、`+` 插入菜单、`Aa` 排版、媒体/附件、文字选区、键盘/光标状态和实际编辑能力。
- 交付采用分阶段方式，但分阶段不代表永久删减。建立可追溯的 AppFlowy 能力对照清单，每项状态明确标记为「已实现并验证 / 开发中 / 计划实现 / 暂缓或受限」。
- 任何不能按 AppFlowy 原有方式实现的能力，必须记录具体技术、许可或 DailyNotes 数据安全原因、影响范围、替代交互和后续方案；若确实需要改变最终能力范围，须向用户说明并取得明确确认。禁止静默删除、假按钮占位，或把计划/暂缓项目表述为已完成。
- 当前可追溯源码参考点采用 R002 固定的 `AppFlowy-IO/AppFlowy@8fcee27d9bd93aad4ee0191d5d8d915d6a9a4e93`；功能盘点时也需关注官方后续演进，但不得未经审查自动改变已确认的对标基线。
- 本条不等于复制整个 AppFlowy 产品、云服务或数据模型；不自动授权复制上游代码/品牌资产，也不代表已选定 `appflowy_editor` 依赖。许可审查、DailyNotes 手机唯一权威存储、混合分层文档格式以及日记/笔记/长期追加各自保存规则继续有效。

## 0.8 第一阶段页面分层：业务信息 + AppFlowy 正文（DN-195）

- 用户已确认：编辑器顶部呈现 DailyNotes 自身的业务信息；下方富文本正文尽可能 1:1 对标 AppFlowy 完整应用手机端，不另建受限编辑器。
- 普通笔记：顶部为独立、可编辑的文档标题，正文 H1 不自动等同业务标题。
- 普通日记：顶部为日记日期及可选标题；新建后直接聚焦正文，不强制先填写标题/分类。
- 长期记录追加：顶部为所属长期记录名称、追加日期与时间信息；仍按业务追加项 ID/时间与草稿正式提交规则管理。
- 三者共用正文画布、区块、光标/选区、动态工具栏、键盘与菜单；不同业务的保存边界继续遵守 DN-009/010、DN-020/021、DN-045/047，手机是唯一权威正式存储，WebDAV 仍只手动触发。
- 顶部业务信息与正文已按 DN-196 确认同区纵向滚动，不再列为待决。仍待逐项讨论：精确尺寸、标题空值/默认名称、日期可编辑性、时间口径及保存状态的位置/时机；不以示意草图当作最终尺寸或真实 APK。

## 0.9 第一阶段滚动行为：业务信息与正文共同滚动（DN-196）

- 用户明确确认：普通笔记标题、日记日期/可选标题、长期记录名称及追加日期/时间位于正文上方，并与 AppFlowy 风格正文位于**同一个纵向可滚动内容区**。
- 向下滚动长文时，业务信息自然离开屏幕；滚回顶部即可再次看到。**不得将业务标题或日期固定在正文上方持续占用编辑空间。**
- 返回/必要操作栏及键盘上方的动态格式工具栏是独立 UI 控制，不要求跟业务信息一起滚动；具体固定方式、操作项与尺寸仍未确认。
- 正文 H1 与业务元数据仍分离。滚动、光标、选区、中文输入法、键盘避让及保存的实际体验需后续真机验证；各业务保存规则与手动 WebDAV 边界不变。
- 本条正式解决 DN-195 的「是否共同滚动」未决项；R015 第七节记录后续确认并保留历史研究提议供追溯。

## 0.10 第一阶段阅读/编辑双态：新建即编辑、已有记录先解锁（DN-197）

- **新建普通笔记、普通日记、长期记录新追加草稿：** 直接打开共用 AppFlowy 风格编辑器，正文自动聚焦，系统键盘自动弹出，进入可编辑状态；不需要额外「解锁」操作。
- **打开已有正式记录：** 默认进入锁定阅读态。可滚动、选择/复制文字和打开链接，但正文、业务标题及文档区块不可被改变；点击正文或复选框不得误进入编辑，系统键盘和编辑格式工具栏默认隐藏。
- **从已有记录进入编辑：** 必须由用户点击「解锁」按钮，才允许开始修改正文和可编辑业务信息。该按钮只负责防误触编辑状态切换，不属于密码/生物识别/加密认证。
- 阅读/编辑仍使用同一编辑器，保持 DN-195/196 的业务信息与正文共同滚动、DN-180/181/182 的 AppFlowy 风格格式栏、DN-020/021 日记自动正式保存、DN-045/047 笔记自动本机保存及失败保护、DN-009/010 长期追加草稿与正式提交边界、DN-187 手机权威存储及手动 WebDAV。
- 已有长期记录正式追加项进入默认阅读态；它是否具备历史修改权限仍由专门业务要求决定，本条不隐式扩大权限。
- **尚未确定：** 点击解锁是否立即弹键盘、是否有「再次锁定」入口、按钮准确位置/样式、存在未持久化内容时的模式切换保护；具体交互建议与未来验收清单见 R016。
- 本条对「新建与已有记录的初始编辑状态」作明确要求；不授权应用编码。

## 0.11 第一阶段解锁后输入与重新锁定（DN-198）

- **已有正式记录点击「解锁」：** 只切换为可编辑态，不自动聚焦正文/业务标题、不弹系统键盘，保持当前滚动位置。用户再次点击正文或允许编辑的业务标题时，才出现光标、键盘和按 AppFlowy 行为呈现的格式工具栏。
- **已解锁状态可随时「重新锁定」：** 用户无需退出记录，便可请求切换回只读阅读态。内容完成本机持久化/妥善保护后收起键盘、隐藏编辑栏，阅读与复制仍可用；锁定后无法意外修改文本、标题或勾选文档内清单。
- **保存不能因锁定而丢失：** 日记和笔记保持各自自动保存/失败保护。存在在途保存时须避免抢先显示保存完成；保存失败时保留内容、明确风险、支持重试/复制，不自动丢弃或掩盖错误。长期记录新追加草稿不得因重新锁定而自动正式提交。
- **保持现有规则：** DN-197 新建内容直接弹键盘不变；DN-195/196 业务信息与正文共同滚动不变；DN-180/181 原版动态工具栏与 DN-187 手机权威存储及手动 WebDAV 不变。
- **未定稿事项：** 锁按钮视觉/位置/是否固定、锁定等待本机保存的交互反馈、动画和编辑历史处理等需要在后续设计与真机验收时确定，不由本条擅自锁定。
- 研究追记：`docs/research/DailyNotes_AppFlowy_Existing_Record_Read_Lock_New_Record_Edit_R016.md` 第七节。

## 0.12 第一阶段输入、列表和中文 IME 复刻原则（DN-199）

- 用户已采纳：Enter、Backspace、列表增/减缩进和撤销重做的**编辑语义尽可能以 AppFlowy 完整应用为准**，避免 DailyNotes 为这些基础动作另外发明一套规则。

- 本地存储、历史备份、同步协议细节、PC Web 工作台等技术方案均须另行设计和确认。

## 7. 继续讨论与工程验收（非已批准的精确参数）

1. Aa 菜单到底采用与 AppFlowy 原版一致的内嵌空间，还是 3.0 已选择的半屏可拖动底部面板，必须记录实际操作差异与对体验、中文 IME、可见正文空间的影响；需要变更已确认 DN-205 时，须先征求用户同意。
2. 精确面板高度、滑动阈值、滚动安全距离、选区偏移和自动滚动锚点；键盘 composing 文本安全、预测性返回取消、旧选区/跨文档失效时序。
3. 智能自动保存的 500ms 防抖与持续输入最长写入间隔（曾建议 2s）均为待实测初值，须验证数据库事务、断电一致性、SQLite WAL/同步设置及存储不足下的 UI 反馈。
4. R1 故障恢复：区分 IO 错误与真正数据库损坏；保护原库及 WAL，避免破坏性修复；在隔离位置校验备份后恢复；强制终止后的未提交内存数据不能保证恢复。
5. 应急 ZIP 候选结构：`manifest.json`、`documents/*.json`、`attachments/*`、`previews/*.md`、`recovery-report.json`；文件大小、SHA-256、引用完整性、部分缺失状态、读回与解密重验。具体字段/算法与导入默认冲突策略尚未最终批准。
6. AES ZIP 候选：优先 AE-2，标准 WinZip AES 的兼容性，不私改密码派生规范；强密码与密码遗失风险、Unicode/UTF-8 密码、Zip64、第三方解压器版本与 Android 导入导出流式处理需后续实测。
7. 默认新建恢复副本、隔离恢复区、附件缺失时知情部分恢复、ZIP 路径穿越/压缩炸弹保护均为安全设计建议；最终页面与验收细则待后续逐项确认。
8. 目前尚未执行加密 ZIP 实际生成、Windows 7-Zip/WinZip 解密、Android 真机、数据库故障注入、应急包重新导入等端到端测试，不能标记测试通过。

## 10. 备份管理、数据健康与故障保护：候选详细规格（非独立批准项）

### 10.1 备份管理中心（V3.13～V3.14）

- 页面候选：备份占用概览、历史备份倒序列表、详情页与空间风险提醒；展示创建时间、备份范围、文件大小、文件 SHA-256、本机位置与授权有效性、远端存在与读回状态、隔离恢复演练状态。
- 状态必须细分为：本地文件存在、字节验证通过、上传完成、远端重新下载后校验通过、恢复演练通过、部分完整、失败、位置不可访问。任何一个状态不能替代其他状态。
- 坚果云 WebDAV 的上传、重新下载/验证、删除和增量同步均为**独立的手动操作**；只依据本地历史记录提醒，不可因后台健康检查发起远端请求。
- 历史清理候选门槛：明确副本身份、独有历史范围、可验证的替代副本与人为确认。不得无条件以年龄或数量自动删包；文件移动/SAF 授权失效标记“需重新定位”，不能误称损坏。
- 单个大 ZIP 是否能上传、上传限制、分卷或分批导出、内部清单与恢复格式均待技术验证，不能改变 DN-215 的已确认标准加密 ZIP 格式。

### 10.2 温和主动提醒（V3.15～V3.16）

- 候选风险等级：正常、需要关注、高风险、未验证/无法判断。手机空间不足与备份占用大不是同义；坚果云离线与远端文件丢失不是同义。
- Android 系统通知需要用户主动许可；普通提醒以页面内为主，锁屏通知不包含日记标题、正文、附件名或密码；相同风险合并，不以点击“已知晓”作为修复完成。
- 已确认系统通知最短间隔与滚动上限见 DN-219；“缺少独立副本持续 7 天”、暂缓 24 小时/7 天、静默通知渠道等均为待验证建议，未当作用户批准的精确阈值。
- 风险解除只能由相应检查证据驱动：保存失败应由最新版本实际提交及读回证明；远端未知应由用户发起真实验证；ZIP 损坏须核实替代可恢复来源。解除提醒与解除风险应分离。

### 10.3 数据健康诊断（V3.17～V3.18）

- 候选页面采用简洁概览 + 专业详情：SQLite 结构和关系、富文本 Document/Block、附件引用与哈希、备份及恢复能力、手机空间与保存状态共五项。
- 深入检查候选流程：受控一致性快照、SQLite quick_check / integrity_check / foreign_key_check（按范围分开）、业务关系核验；富文本 JSON 与稳定 Block 树、revision；附件流式 SHA-256。SQLite 检查通过不等于业务数据健康通过。
- 深入扫描仅由用户主动发起，资源让位于编辑保存；按完整检查单元登记可恢复进度，SQLite 单次 integrity_check 中断后不能凭虚构页进度续跑。文档 revision 与扫描快照发生变化时，结果只代表原快照。
- 诊断证据台账建议记录 checkId、scope、snapshot/revision、cursor、status、errorCode、结果及检查时间；区分“流程完成”与“内容通过”，不写日记正文，不将台账当作第二权威数据库。
- 修复流程必须先保护原件及必要 WAL/附件，再在隔离位置验证恢复候选并展示差异；诊断页面不自动重建/覆盖原库。低空间、强杀、损坏库与不可读附件需要端到端异常测试。

### 10.4 P2 严重保护（V3.19～V3.21）

- 候选状态：P0 正常、P1 原因待确认并临时保护编辑、P2 已确认严重结构问题并阻断危险正式写入。BUSY/FULL 等不能直接当成 CORRUPT；不可确定时保留分类诊断入口。
- P2 当前文档可继续进行有效的内存文本/Aa 编辑；固定风险条和导出入口，不能显示本地已保存。原库/附件/历史保留；PC 正式提交不能绕过手机保护；坚果云保持手动。
- 应急 ZIP 必须以真实冻结快照为基线，区分文件完整性、内容新鲜度、声明范围及附件缺失；新文字、格式、Block 或附件变化后，旧 ZIP 仍可用但不再代表最新版本。验证通过须真实写入并从文件读回、解密和核验。
- P2 使用一个活跃内存编辑会话；其他文档可受控只读预览。普通切换编辑需要最新版本的完整有效副本和人工确认；强制终止后仅可靠恢复持久化版本，风险退出需要明确确认。
- 恢复应创建独立候选、比较历史版本与当前应急内容；不得自动用旧备份覆盖新内容。恢复后必须验证数据库结构、Block、附件、revision、删除状态及新工作库提交与重开读回。
- 固定风险条、持续编辑的首次 2 分钟/后续 5 分钟提示、P2 新增附件写入限制、Aa/IME 安全暂停与候选切换算法属于具体实施提案，未独立批准精确交互阈值。

## 11. AppFlowy 风格导航、Block 与书签：候选详细规格（V3.22～V3.26）

### 11.1 多级 Block 和目录抽屉

- 编辑器统一使用稳定 Block ID 与父子关系；标题 H1/H2/H3、段落、列表、Toggle、Toggle Heading、图片/附件等按真实能力分阶段实现，不随意删减目标范围。
- 对 Enter、Backspace、Tab/缩进、撤销重做、中文输入和跨 Block 选区应与正式 AppFlowy 移动版逐项对照。结构移动要保留原 ID/子树，避免循环与孤立；一个多块移动是一个语义撤销事务。
- 右上角目录按钮打开右侧抽屉；目录折叠与正文 Toggle 折叠独立。目录内搜索按标题/允许显示的 Toggle 过滤，临时展示命中路径，清除搜索后恢复原目录折叠状态。
- 点击目录目标先处理有效 IME composing，再展开遮挡目标的正文祖先、以 Block ID 定位；关闭抽屉后不自动唤起键盘。Flutter 局部渲染、实际滚动定位和选区有效性仍需真实代码与设备验证。

### 11.2 阅读锚点、编辑光标与临时返回

- 双位置分别建模：readerAnchor 记录文档 ID、Block ID、块内安全逻辑偏移、视口相对位置、原文档修订；editorCaret 记录用户最近有效输入焦点位置。两者不可互相覆盖。
- 新开已有记录首先恢复阅读锚点、默认锁定阅读；用户解锁后仍需主动点击正文才进入输入。定位旧编辑位置不自动等于聚焦或弹出键盘。
- A→B→返回 A 首选当次跳转前的临时返回点，不被 A 的旧全局阅读锚点取代；同篇多次目录跳转可提供“上一位置”。返回历史的持久化策略、上限与多窗口边界尚待选择。
- 阅读位置元数据自动、合并写入；写入失败使用最后成功记录的锚点，不误报当前已保存。Block 删除/移动/文本变长、字体缩放、图片加载需通过稳定身份与布局修正定位；不可靠位置应安全回退而不是误选其他文档。

### 11.3 轻量手动书签

- 用户确认书签范围为添加、命名、删除、跳转，不引入复杂分组/标签；建议默认书签名引用当前标题但允许用户修改，不修改正文标题。
- 候选模型使用 bookmarkId + documentId + blockId + 可选块内偏移 + 名称。书签应独立于业务正文修订和阅读位置，用户创建后主动持久化，失败应显示待重试而非成功。
- 书签目标失效时保留原关联与失效状态，不按同名标题自动重绑；支持人工查看上级/邻近候选并明确确认重新绑定；书签删除仅影响其元数据，提供有限撤销。
- 跨文档书签跳转继承阅读模式、返回点与未保存修改保护；P2 中遵守只读预览和正式写入禁止。书签纳入何种整库/单文档备份范围及迁移映射须按已有备份契约核验。

### 11.4 长篇笔记性能

- 以约 100、1,000、10,000 Block 及混合图片/表格/嵌套结构构造实测样本；编辑延迟、滚动卡顿、内存、搜索、目录跳转、中文 IME、撤销重做和持久化成功均需真机端到端检查。
- 保持完整文档逻辑模型与稳定映射，按视口优先绘制、附件延迟解码、增量目录索引，但不得简单使用普通列表虚拟化而破坏跨 Block 选区、输入法状态及撤销栈。窗口大小、层级上限和帧率阈值尚未批准。

## 15. 附件、媒体与编辑器协同的候选详细规格（非新增正式独立批准项）

### 15.1 图片 / PDF / 音频的一致数据边界

1. 图片按 DN-229～DN-231 独立 Block 展示与手柄排序；移动 Block 应保持稳定 Block/业务身份、附件引用和历史，不因为拖动就复制附件字节。图片主体长按进入操作菜单，短距离移动和远距离移动使用不同入口。
2. PDF 按 DN-232 显示紧凑卡片；独立阅读器应支持从原文档打开与返回、记录物理页阅读位置，与正文阅读锚点互不覆盖；印刷页、缺页/扫描件、阅读缩放、全文搜索能力需按文件能力逐项验收，不推定所有 PDF 可选中文本。
3. 音频会话与当前正文编辑相互独立。长期录音需按需解码、保存进度与标记；具体 8 小时规模是压力测试目标而非已证明可以稳定播放。后台播放关闭时，离开 App/锁屏应按开关规则暂停；允许后台时需遵守 Android/HyperOS 的实际限制，不做无限后台承诺。
4. 媒体标记、PDF↔音频关系、正文引用分别是不同业务对象和事务。标记或关系的成功写入不能让正在失败的正文显示“本机已保存”；正文锁定不阻止独立媒体标记，但插入正文必须解锁。
5. 富文本正本仍按 DN-183 使用具有完整 Block/行内属性的 Document JSON 方向；附件内容身份、内容版本、引用及历史由 DailyNotes 独立管理。不能把原机绝对路径作为唯一附件身份，也不能用普通纯文本导出冒充无损正本。

### 15.2 PDF ↔ 音频双向关联及自动跟随

- 关系候选字段：稳定 relationId、pdfAttachmentId/pdfContentVersion/physicalPage、audioAttachmentId/audioContentVersion/offsetMs、关系修订、操作 ID、删除墓碑。创建时冻结当前 PDF 页与录音毫秒位置；不修改原 PDF、录音字节或当前笔记正文。
- 默认手动两端跳转；显式开启自动跟随后，优先响应自然播放跨越的有效关联时间点。用户手动翻页、缩放、调整进度条时暂停；建议提供“恢复跟随并同步当前时间”入口，不偷偷恢复。
- 同一时刻多条关系指向同一页，可合并一次视觉定位但保留独立关系；同一时刻指向不同页则不随机选页，建议暂停并让用户选择。精确冲突时间窗口、Seek 到旧时点、多个不同 PDF 的目标选择均未确认。
- PDF 或音频内容版本变化、文件不可用、关系已删除时，不凭文件名、相同页数或毫秒位置自动重绑。人工校验后明确重绑应保留旧版及操作历史。关系删除采用非破坏性历史记录的候选模型，不物理删除两端附件。
- PDF 阅读器关闭、用户在其他笔记输入或屏幕锁定时，不因跟随而强制打开 PDF 或抢夺 IME/阅读焦点。页面加载慢时过时定位请求不能反向覆盖最新请求。
- 这些规则作为 V3.39～V3.40 的工程候选与验收依据，具体物理存储 Schema、缓存索引、音频事件源和实时阈值未批准，也未编码。

### 15.3 统一编辑器三业务及顶部状态

- 日记/笔记/长期追加共享 AppFlowy 风格的完整正文编辑体验，遵守 DN-193～DN-203、DN-204～DN-210；新建直接编辑与唤起键盘，已有正式记录默认阅读锁定、解锁后还需用户点正文才弹键盘。长期正式历史项目的历史修改权限仍由独立业务规范决定。
- 业务头部与正文共同滚动（DN-195～DN-196）；普通笔记的文档标题、普通日记的日期/可选标题、长期追加所属记录与日期时间为业务信息，和正文 H1 分离。顶部返回、文档目录、锁定、保存状态属独立操作栏，不等于固定业务标题。
- DN-240 顶部状态建议至少区分：已保存当前修订、修改待保存、正在写入、写入失败、P2 保护。点击显示当前对象的 revision 与错误细节；其他文档的未保存风险另用跨页风险条/数据状态中心表达。正常成功不频繁弹 Toast。
- 保存任务应以被冻结的目标修订入库；若旧修订写入中发生新编辑，旧修订成功不等于最新版本成功。禁止使用单个全局 saved 布尔值或把 WebDAV/LAN 状态冒充本地持久化。
- 同一 App 内轻量迷你播放器随笔记/PDF/日记页面存在；键盘展开时采用不遮挡当前输入行和格式工具栏的紧凑布局。该布局是产品候选，真实 Android IME 高度、底部安全区、横屏/字体缩放尚须验收。
- Aa 主面板仍遵守已批准的 DailyNotes 半屏可展开方案 DN-205，并明确与 AppFlowy 官方标签源码的键盘区域内嵌 Aa 不同；编辑器 + 仍采用 AppFlowy 原版纵向菜单。系统返回关闭 Aa 不自动弹键盘；点击 Aa“完成”仅在原选区/焦点仍有效时有条件恢复（DN-207）。最新官方 Android APK 的逐动作结果未实测，不声称完全一致。

## 16. 长期追加及异常退出的候选状态机（非新增正式独立批准项）

1. 用户在长期记录旁点“追加”→ 创建稳定 draftId 的新草稿 → 立即进入完整编辑器并聚焦正文；已存在草稿从该长期记录详情进入，同一 draftId 不复制内容；所属记录详情把待提交草稿与正式历史分区。
2. 草稿编辑期间遵守智能本地保存，但“草稿已保存到手机”与“正式追加成功”必须分别可见。普通日记和笔记自动保存即正式内容；长期记录明确正式提交，不能由锁定、关闭 Aa、返回、媒体标记或自动保存隐式完成。
3. 正式提交候选事务：核对最后成功落盘的草稿修订、原 recordId、富文本格式版本及必要附件引用，通过同一 operationId 的幂等 CAS 提交生成唯一 appendId 并更改草稿状态。明确成功后按 DN-239 返回所属长期记录按 appendId 定位，草稿不再显示为待提交。
4. 提交明确失败时继续保留草稿；结果未知（可能数据库已执行但回执丢失）时必须按原 operationId 查询，不直接新建另一条 appendId，也不能凭 UI 动画声明成功。筛选列表隐藏新历史项时可建议提供临时定位入口，而不擅自改动用户筛选。
5. 草稿删除/恢复的候选为软删除与恢复原 draftId，保留 revision、操作日志、附件引用及原所属记录；不因正式提交就直接物理删除可能含独有历史的草稿数据。具体清理期不在此锁定，遵循旧版垃圾回收与回收站保护规范。
6. 导航统一保护：普通保存失败允许其他记录安全只读浏览，保留原活跃手机正文编辑缓冲，阻止第二个冲突手机正文编辑会话；普通返回优先处理有效 IME/键盘/Aa 上下文。新建长期追加已落盘仍未正式提交时，继续遵守 DN-009/010 保留草稿返回或继续编辑的退出确认。
7. 普通 I/O 保存失败不自动等于 P2。已确认 P2 时，依 DN-221～DN-223 原活跃文档仍可继续内存文本和必要排版，所有对受损正式库的危险写入必须阻断，其他文档仅安全只读预览；应急 ZIP/复制入口持续可达。正式 ZIP 需采用既定 WinZip AES-256、写入后读回解密核验，旧 ZIP 不代表最新编辑。
8. 单活跃编辑会话的细则不能覆盖 DN-187：PC 仍可作为手机批准的远程编辑端发起正式操作，手机权威端须通过 revision/CAS 和操作幂等识别冲突。PC 断线草稿与本机未保存草稿如何协同需工程设计，禁止默默后写覆盖。

## 21. 跨页、恢复与风险状态的设计候选（不自动视为已批准）

### 21.1 单活跃编辑会话、Aa、PDF、音频

- 应用仍活跃时，打开 Aa、目录抽屉、关联 PDF、音频播放器和恢复报告，不得用历史数据库版本重建并覆盖原未保存正文；旧保存任务的回执不能冒充最新修订成功。单一活跃手机正文编辑会话应保留，其他资料可安全只读查看；不覆盖 PC 经手机批准的 LAN 远程编辑架构。
- Android IME composing、安全选区、预测式返回、半屏与横屏 Aa、旋转、单行播放器和最小可编辑区域需要 Android 实机复现与验证。系统返回关闭 Aa 不自动弹键盘（DN-207）；已有记录阅读锁定、解锁后点正文再聚焦（DN-226）。
- PDF 阅读位置和正文编辑位置分别记录。PDF/音频关系或独立音频标记成功，不代表正文保存成功；后台播放是默认关闭的独立设置（DN-234）。长音频 Media3 和 PDF 渲染并未真实验证。

### 21.2 冷启动、在途事务、R1 与长期追加

- 区分切后台进程仍活跃与系统强杀/进程死亡。后台触发保存检查不能代替真正持久化提交证明；R1 只保证最后有效版本。不能声称知道未持久化正文具体丢失多少，除非具有相应可靠证据且仅如实报告。
- 在途本机保存或长期正式追加回执丢失时，候选以持久可核对的 operationId 检查“确实提交/确实未提交/仍无法判定”。无法判定时不盲目重复正式追加或覆盖数据；成功时读取真实唯一 appendId。
- 长期追加草稿只在所属长期记录中恢复同一 draftId 和已保存草稿版本。正式提交必须独立明确成功；用户返回或 PDF/音频操作不能自动发布草稿。
- R1 历史恢复事件可有单独的 recoveryEventId 与确认元数据；同一可信证据重复扫描应去重，新独立事件需新身份。风险确认成功后收起普通提示，历史报告保留；失败或结果未知时不谎称知悉已持久化。一个记录多个事件按稳定 documentId 分组。

### 21.3 统一健康证据、风险中心与 P2 安全

- 数据健康检查（DN-175、DN-220）负责健康概览、只读诊断证据与手动深扫；恢复风险中心负责事件、知悉、未知事务与报告。两者可共用证据 ID，但不能互相伪造业务状态；未核验部分不得标健康。
- 正常 I/O 错误、空间不足、锁竞争与真实严重结构损坏必须区分。P2 确认后由**底层写入隔离**强制阻断受影响正式库的危险写入，不能通过普通返回、PC 请求、系统通知或 R1 知悉绕过。
- P2 且原进程存活时，保留**原活跃内存编辑**、必要排版/复制/应急抢救；强杀后原内存会话已不存在。旧 ZIP 不代表保护了最后未保存内容；正式应急副本须按既有规范加密、核验与隔离读回。

### 21.4 应用内提醒与 Android 系统通知

- 应用内正在发生的保存失败/P2 必须即时可见，不受系统通知限频；R1 可单事件知悉，未知事务须真实核验，不得通过“已读”结束。全局风险入口按 DN-249 仅有风险时显示，不占用日记 DN-164 四个已确认快捷菜单。
- DN-218～DN-219 既定同类高风险系统通知**至少间隔 72 小时、滚动七天最多两次**；普通风险优先在应用内。限频、未授权、被清除或系统未展示通知都不改变底层风险状态，也不允许后台自动执行坚果云 WebDAV。
- Android 通知点击前核对当前 P2、应用隐私锁、eventId/operationId/documentId 和实际版本；旧通知或重复点击不自动确认 R1、重新提交长期追加或解除保护。存活进程保留原编辑缓冲和安全返回栈；冷启动先核验最后有效版本；来源无法安全定位时进入替代入口。
- 具体的 PendingIntent 唯一性、通知渠道、密级、启动任务栈、首次/升级分类和符合“重要且持续”条件的判定，仍是**待批准和待真机测试的技术细则**，并非用户批准的固定通知调度算法。
